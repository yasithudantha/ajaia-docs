# Architecture & Product Prioritization Note

## 1. System Architecture

```text
+-----------------------+        HTTPS + X-User-Id        +---------------------------+
|   React + Vite SPA    | ------------------------------> |   Express 5 REST API      |
|   (Vercel Frontend)   | <------------------------------ |   (Vercel Serverless)     |
|  - Tiptap Rich Editor |        JSON / Multipart         |  - Role/Owner Authz       |
|  - Tailwind CSS v4    |                                 |  - Multer + Marked/Mammoth|
+-----------------------+                                 +---------------------------+
                                                                        |
                                                                 SQL (pg Pool)
                                                                        v
                                                          +---------------------------+
                                                          |   Neon PostgreSQL         |
                                                          |  - users                  |
                                                          |  - documents              |
                                                          |  - document_shares        |
                                                          +---------------------------+
```

### Data Model (Neon PostgreSQL)
- **`users`**: Seeded workspace accounts (`id`, `name`, `email`, `role_label`).
- **`documents`**: Stores `id`, `title`, HTML `content`, `owner_id` (FK -> `users.id`), optional `source_filename`, `created_at`, and `updated_at`.
- **`document_shares`**: Join table with `(document_id, user_id)` unique constraint and `permission` (`'viewer'` | `'editor'`).

### Security & Access Enforcement
- Even though user switching is streamlined for evaluator convenience via an `X-User-Id` request header, **every read, update, delete, and share endpoint resolves effective permissions in SQL** (`owner` vs `editor` vs `viewer` vs `null`).
- Unshared users receive `403 Forbidden` on `GET /api/documents/:id`; `Viewer` collaborators receive `403 Forbidden` on `PATCH /api/documents/:id`; non-owners receive `403 Forbidden` on `DELETE` and `/shares` endpoints.

## 2. What Was Prioritized & Why
1. **End-to-End Vertical Slice Over Shallow Features:** Delivered full CRUD, rich formatting, file import, role-based sharing, automated integration tests, and a live zero-cold-start deployment rather than half-finished real-time widgets.
2. **Product-Relevant File Import (`.md`, `.txt`, `.docx` -> Editable Document):** Converting uploaded files directly into structured HTML inside Tiptap makes file upload an active part of the authoring workflow rather than a passive blob attachment.
3. **Zero-Friction Evaluator UX:** Replaced OAuth/password signup walls with seeded realistic personas (`Alice`, `Bob`, `Carol`) and a 1-click switcher so reviewers can verify multi-user sharing flows in under 10 seconds.
4. **Role-Based Permissions (`Owner`, `Editor`, `Viewer`):** Added `Viewer` vs. `Editor` differentiation to demonstrate meaningful backend authorization and conditional UI locking.

## 3. Intentional Scope Cuts & Tradeoffs
- **Explicit Save vs. Real-Time CRDT/WebSockets:** Implemented explicit save state tracking (`Unsaved changes` / `Saving...` / `All changes saved`) with PostgreSQL persistence instead of Yjs/WebSocket conflict resolution, avoiding distributed state complexity within a 4-hour timebox.
- **HTML Persistence vs. Raw ProseMirror JSON:** Persisted HTML generated by Tiptap, `marked`, and `mammoth` so imported files and rich-text edits share a single uniform storage representation.
- **In-Memory Multer Processing:** Files (capped at 2 MB) are parsed in memory and converted directly into database records, eliminating S3/object-storage infrastructure dependencies.
